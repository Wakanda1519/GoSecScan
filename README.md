# 🛡️ GoSecScan

**Консольный сканер веб-уязвимостей на Go: перебирает эндпоинты по словарю, проверяет Reflected XSS и SQL-инъекции, а при первом запуске сам создаёт базу сигнатур `config.json`**

## Особенности

* Автономность: если рядом нет `config.json`, он создаётся автоматически со встроенной базой сигнатур; если есть — просто читается.
* Worker Pool на горутинах и каналах, число потоков задаётся флагом `-t`.
* Три режима: `dir` (поиск эндпоинтов), `xss` (Reflected XSS), `sqli` (Error-Based SQLi).
* Smart 404: калибровка по длине тела кастомной 404-страницы, чтобы отсекать ложные `200 OK`.
* WAF Bypass: при кодах `429` и `5xx` воркер делает случайную паузу 500–1500 мс.
* Пассивный сборщик (Spider): вытаскивает зацепки (`todo`, `api`, `debug`, ...) из HTML-комментариев на успешных ответах.
* Встроенная база: 292 `dir_endpoints`, 61 `xss_payloads`, 74 `sqli_payloads`, 81 `sqli_errors`.
* Единственная зависимость — стандартная библиотека Go.

## Ограничения

* Только GET-запросы без авторизации, куки и кастомных заголовков — приватный функционал не проверяется.
* Редиректы не разворачиваются: `301`/`302` показываются как есть.
* Параметр инъекций зафиксирован как `search` (`?search=...`); под свой параметр нужно править код.
* `xss` ловит только отражение пейлоада, `sqli` — только error-based по сигнатурам: это эвристики, а не доказательство уязвимости.
* Инструмент предназначен только для тестирования своих систем или целей, на которые есть разрешение.

## Установка

### Требования

* Go 1.26+
* Цель, на которую есть разрешение на тестирование

### Сборка

```
go build -o gosecscan .
```

### Использование

| Флаг | По умолчанию | Назначение |
|------|--------------|------------|
| `-u` | — (обязателен) | Целевой URL, например `https://example.com` |
| `-m` | `dir` | Режим работы: `dir`, `xss` или `sqli` |
| `-t` | `10` | Количество воркеров |
| `-w` | — | Дополнительный словарь путей (мёржится с `dir_endpoints`) |
| `-c` | `config.json` | Путь к базе сигнатур |

1. Первый запуск создаст рядом с программой `config.json` со встроенной базой — файл можно и нужно дополнять своими путями и пейлоадами.
2. Режим `dir` перебирает пути из `config.json` (плюс `-w`, если задан) и печатает всё, что вернуло `200`/`301`/`302`.
3. Режим `xss` шлёт пейлоады в `?search=` и сообщает об отражении в теле ответа.
4. Режим `sqli` шлёт пейлоады в `?search=` и ищет в ответе сигнатуры ошибок СУБД.

```
go run main.go -u https://example.com -m dir -t 20
go run main.go -u https://example.com -m dir -w wordlist.txt
go run main.go -u https://example.com -m xss
go run main.go -u https://example.com -m sqli -c config.json
```

## Вопрос - ответ

<details>
  <summary><b>Зачем нужен config.json и можно ли без него?</b></summary>
  <br>
  Без него можно: при старте программа проверяет наличие файла и, если его нет, создаёт со встроенной базой сигнатур. Если файл уже существует — просто читает его и ничего не перезаписывает.
</details>
<details>
  <summary><b>Что такое Smart 404?</b></summary>
  <br>
  Перед сканированием режима dir отправляется запрос на заведомо несуществующий путь и запоминается длина тела ответа. Если сервер отдаёт кастомную 404 со статусом 200, любые ответы 200 ровно такой же длины отбрасываются как ложные срабатывания.
</details>
<details>
  <summary><b>Почему появляются паузы "anti-ban"?</b></summary>
  <br>
  При кодах 429 и 5xx воркер делает случайную паузу 500–1500 мс, чтобы не перегружать сервер и обходить rate limit. Скорость падает, зато скан не упирается в блокировку.
</details>
<details>
  <summary><b>Почему скан завершился, а результатов нет?</b></summary>
  <br>
  Значит ни один путь не вернул 200/301/302 — сервер отвечает 404/403 на всё из словаря. Частый случай для SPA: тогда смотрите API, статику сборки и robots.txt/sitemap.xml.
</details>
